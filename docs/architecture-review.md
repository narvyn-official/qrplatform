# QRPlatform Architecture Review

## Runtime Shape

QRPlatform is a Django monolith backed by PostgreSQL, Redis, Celery, and
Whitenoise/static-file serving. Browser pages are rendered through Django
templates, while `/api/v1/` exposes authenticated DRF endpoints. Celery handles
periodic analytics, image regeneration work, scan-event enrichment, and email
jobs.

## Core Data Flow

1. Users authenticate through `apps.accounts` and receive a role/plan from the
   membership catalogue in `apps.accounts.plans`.
2. QR CRUD requests enter through dashboard views or DRF serializers.
3. Plan limits are checked before create/clone/API create.
4. QR payload, destination, design, schedule, expiry, scan-limit, and premium
   field validation is shared through `apps.qrcodes.validation`.
5. QR image files are generated by `apps.qrcodes.tasks`.
6. Scans hit `/r/<short_code>/`, pass status/schedule/password/plan checks,
   create a `QRScanEvent`, and process the event immediately with Celery retry
   fallback.
7. Scan processing updates denormalized QR counters and daily/hourly/geographic
   analytics aggregates.
8. Dashboards and API summaries read aggregate tables first and fall back to raw
   processed scan events for dates that have not been aggregated yet.

## Critical Problem Areas

- Validation and plan enforcement can drift when duplicated across forms, API
  serializers, and views. Shared validation and quota services reduce that risk.
- Analytics reads should avoid raw scan-event sweeps once aggregate rows exist.
  Raw events should remain the write-audit trail, not the primary dashboard data
  source.
- `qrcodes.views` and `accounts.views` are large controller modules. They mix
  request handling, business rules, orchestration, and UI context construction.
- Payment activation, QR generation, scan processing, and analytics aggregation
  are service workflows but still partly embedded in views/tasks.
- Dynamic redirect is the highest-traffic path. Any added blocking work there
  can directly affect customer scans.
- Model methods contain some business logic, but cross-model workflows need
  clearer service boundaries to stay testable at scale.

## Refactoring Strategy

- Keep Django apps as bounded domains, but move reusable business rules into
  small services/selectors:
  - `qrcodes.validation` for input normalization and field validation.
  - `qrcodes.services` for QR quota checks and workflow helpers.
  - `analytics.selectors` for read-model queries.
  - `accounts.billing_services` later for payment activation and order state.
- Prefer aggregate read models for dashboards, with raw-event fallback only for
  freshness and test compatibility.
- Keep redirect-path work minimal: validate, record, increment, redirect. Push
  enrichment, reports, and cleanup to Celery.
- Split large view modules by workflow when making future changes, but do it in
  small behavior-preserving steps with tests around each route.
- Introduce database-level constraints/indexes only with migrations and measured
  query plans, especially on scan-event volume paths.
